# 提交与快照确认

本轮属于 D-08 第四批。生产仍使用 Memory 与周期 JSON 快照，未切换 SQLite，未改变默认 15 秒写盘周期。

## 使用入口

重启新版 Go 并刷新网页，顶部「保存状态」显示当前页面的写入观察。点击查看最近 60 次操作、手动检查快照或打开诊断。备忘录、待办详情与日程编辑显示对应记录的「上次提交」状态；当前继续输入的内容仍需要保存。

| 状态 | 含义 |
| --- | --- |
| 正在提交 | 等待业务响应，不重复点击。 |
| 已提交 · 等待快照 | 收到有效业务响应和凭据，尚未观察到覆盖此提交的成功快照。 |
| 已纳入成功快照 | 本次运行中，成功写出的主快照在捕获数据时已越过此次提交边界。 |
| 快照写入失败 | 覆盖此提交边界的快照失败；后续成功快照可以补充确认。 |
| 结果需核对 | 业务响应不明、格式异常、凭据无法验证或服务已重启；回原记录核对，不自动重发。 |
| 已提交 · 无快照凭据 | 业务响应有效，但服务未提供凭据，例如尚未重启的旧服务。 |
| 本次提交未确认 | 请求被拒绝或未发出；结合原页面错误处理，不视为写盘成功。 |

状态只在当前页面内存，不保留标题、正文、请求体或完整响应；登录令牌不写入状态记录。刷新清空观察，原有草稿、日程原提交与离线待办不受影响。清空未确认状态需要明确确认；超出容量的未确认操作保留数量提示，不会让总状态全绿。切账号、换服务、退出清空观察；过期、离线、后台暂停检查。

自动检查最多持续到最近受观察操作后的两分钟，每轮间隔三秒、每批最多 20 个凭据，不重发业务请求；超时后可手动检查。检查失败保留原有结果。

## 服务端协议

范围限定为 `/api/v1/memos`、`memo-folders`、`todos`、`todo-lists`、`todo-imports`、`calendar/events`、`calendar/event-commands` 及其子路径的成功 JSON 写入。鉴权、上传、导出、诊断、只读 POST 不在范围。独立离线阅读器沿用自己的提交与核对界面；本轮不代表整站或所有客户端接入。

1. 已鉴权处理器开始前绑定观察会话，成功操作完成后、发送响应头前产生 `X-Daynest-Write-Receipt`。
2. 账号独立递增边界，进程随机密钥签名并绑定账号。凭据不写入 JSON、日志、URL 或诊断导出。重启或模型替换后失效。
3. `SaveJSON` 在与业务数据相同的读锁内捕获边界；只有主快照全部写出成功才推进成功边界。提前捕获、稍后完成的快照不能确认捕获之后的提交。失败不推进成功边界。
4. `POST /api/v1/system/write-status` 要求登录，请求 `{ "receipts": ["…"] }`，最多 20 个、各最多 180 字符；查询不调用 `SaveJSON`、不初始化业务数据、不改变周期。
5. `data` 包含 `schema_version: 1`、`mode: periodic_json`、`available`、`interval_seconds`、`checking_triggers_write: false`、按输入顺序返回的 `receipts`。各项含 `receipt`、`state`、可选 `snapshot_at` / `failure_at`。枚举：`waiting_snapshot`、`snapshot_written`、`snapshot_failed`、`unverifiable`。其他账号或伪造凭据统一不可验证。

业务 DTO 校验后才认为响应有效。即使快照有覆盖证据，格式异常、错误记录身份、编辑版本异常或新建回执不匹配仍显示「结果需核对」。

## 保证与限制

这是对成功快照的历史观察，不是 WAL / 数据库事务提交、完整备份、当前磁盘完整性或断电持久性保证。快照记录捕获时的最新业务状态；同一记录随后被修改或删除时，不保证每个历史版本独立保留。后续磁盘故障不抹除历史成功。

不比较客户端时间与 `last_success_at` 推断包含关系，不把重载快照当作旧凭据证明。重启后需回读核对；实际处理成功但响应丢失也不会自动成为业务成功。

- Go 测试 / vet；新增捕获边界、失败恢复、账号 / 进程 / 模型隔离、篡改、HTTP 范围与只读查询测试。
