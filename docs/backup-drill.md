# 完整备份恢复演练设计（D-04）

状态：验收设计，尚未执行真实用户数据恢复。目标是建立可重复的恢复流程，为后续 SQLite 迁移提供前置保障。

## 范围与权限

个人 JSON 导出只覆盖所属账号的业务记录，不包含快传目录。完整服务备份会包含多个账号的记录、密码哈希、快传文件及元数据，只能由电脑上的服务所有者执行，不能把它做成任意登录账号都能下载的接口。

完整备份包含：

- 配置的 DATA_FILE 主文件；同目录的 `.bak` 作为可选恢复候选单独标记，不能混同主文件。
- DATA_FILE 同级整个 transfers 目录，保留目录结构、`.blob`、元数据和必要的状态文件。
- 非敏感配置与版本清单：应用 / 数据格式版本、备份时间、各文件相对路径、大小和 SHA-256。密码、令牌、AI 授权、签名密钥等不进入普通诊断或公开产物。
- 旧模块兼容记录、归档及回收站也应保留。过期记录尚未永久清理，不能在备份时擅自删除。

密钥与个人环境配置若要备份，应另行保护。更换 JWT 签名密钥会使原登录失效，但不应导致账号业务记录丢失。备份包本身应视为私密数据，保存位置与保留期限由用户控制。

## 演练步骤

1. 先用测试数据建立基准：至少包含两个账号、待办 / 目标引用、日历联动、备忘录文件夹与正文、文字片段、回收站、过期项、快传文件与元数据。
2. 正常停止对应 Go 服务，确认该进程结束、最后快照结果可核对且没有上传仍在进行。不能仅凭手机访问不到就判断服务已停止。
3. 复制完整范围到新的备份目录，生成清单并检查哈希。复制或校验失败时不能标为成功；保留源文件不做清理。
4. 恢复到另一个独立目录，先执行格式 / 清单 / 哈希预检。未知格式、缺文件、路径越界、符号链接、文件过大或校验不一致应阻止自动恢复。
5. 用独立测试端口与明确的测试 DATA_FILE 启动恢复副本。不得启动两个进程同时写同一数据目录。
6. 验证账号登录、隔离、主要记录字段、跨模块引用、归档 / 回收站、快传下载及内容哈希。不能只数记录条数就判定恢复成功。
7. 保存演练结果：备份标识、应用版本、各项通过 / 失败与缺失文件。普通结果报告不携带业务正文和本机路径。
8. 关闭演练服务。只有演练完成、原数据另有可用副本且用户明确选择切换后，才安排正式数据目录切换。

## 必须覆盖的失败场景

| 场景 | 预期结果 |
| --- | --- |
| 只有个人 JSON，没有 transfers | 明确报告不能恢复附件，不标为完整备份。 |
| 主快照损坏、滚动备份有效 | 按现有恢复语义保全损坏文件，报告采用了较旧版本；逐项核对数据差异。 |
| 主快照与滚动备份均损坏 | 阻止启动或恢复，保留原文件，不创建空数据覆盖。 |
| 附件内容缺失、元数据存在 | 指出缺失文件，其他数据不被误报为完全恢复成功。 |
| 文件哈希不一致或包含越界路径 | 停止恢复，不写到目标目录之外。 |
| 磁盘满、权限不足、复制中断 | 报告失败并保留来源，不以“导出成功”掩盖未完成的副本。 |
| 恢复包混入其他账号或 ID 引用冲突 | 完整服务恢复须在隔离目录验证；将来账号级导入需单独做所有权和引用映射，不能原样信任包内 user_id。 |
| 测试服务与真实服务配置混淆 | 预检阻止向真实目录写入；启动前明确核对目标与端口。 |

D-04 的完成条件是演练结果可重复、故障被明确识别、原数据得到保全。诊断页的 `restore_verified: false` 不会因为增加了这份文档或单元测试就自动变成 true。
