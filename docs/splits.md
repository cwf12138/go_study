## 三步完成一次分账

1. **新建账单**：填写名称、日期，以及 2–20 位成员的称呼。仅由当前账号维护，不要求朋友注册，也不发送邀请或消息。
2. **记录费用**：填金额、付款人、发生日期，选择分摊成员。支持平均分摊和自定义每人金额；付款人可以不参与这笔分摊。同一个账单可以记录不同成员垫付的多笔费用。
3. **核对结算**：查看每人已付、应摊、应收或应补金额，以及净额抵扣后的建议。实际转账在应用外完成；确认全部核对和结算后，手动标记整单结清。

已结清的账单保留历史计算，但不显示新的转账要求。先「重新打开」才可修改成员或费用；重新打开本身不撤销外部转账。**若结清后又追加新费用，建议另建账单**，避免将旧的已付款与新欠款混淆。本功能没有部分结算、实际还款流水、支付凭证或转账追踪。

## 交互与保存

- 账单分为未结清、已结清、回收站；可按账单名、备注或成员搜索，每页 6 个账单。手机上账单卡片可横向浏览，详情位于下方。
- 每个账单最多 100 笔费用，明细每页 8 笔，支持编辑与删除。删除单笔费用需要确认，**没有单笔恢复**；整张账单可移入回收站并恢复，没有永久删除入口。
- 成员使用稳定 ID，修改称呼不改变归属。已有费用关联的成员不能直接移除；需要先编辑相关费用和分摊成员。
- 复制结算摘要后可以自行发给参与者核对；自动复制不可用时提供手动复制框。CSV 导出每笔费用、每位成员的分摊，金额以元表示；一笔费用总额在其每个分摊行重复，**分析 CSV 时不要直接对总金额列逐行求和**。已对以公式符号开头的文本做防护。
- 保存中防止重复提交；超时、断网或未知结果会保留原始请求。关闭弹窗后可在页面顶部「原样重试保存」，不会改变 ID、版本和内容。版本冲突需选择「放弃本次请求并重载」核对，不覆盖其他窗口的更改。
- 校验失败保留编辑内容并允许修改；退出或切换账号清空页面内容和待确认请求，晚到响应不能恢复旧账号数据。未提交的表单不自动保存，刷新会丢失。
- 数据按账号隔离，纳入 JSON 快照和个人 JSON 数据导出。无云同步、银行连接、支付操作或共享编辑；不自动写入生活账本，避免将垫付总额误当作个人消费。JSON 快照本身不加密，请保护备份。

## 金额规则

- 仅人民币，单笔 0.01–1,000,000 元。输入最多两位小数，不接受负数、科学计数或多余小数。后端保存与运算均为 int64 **分**；前端将十进制文本拆成整数分，不用浮点数累计金额。
- 均分例子：100.00 元分给三人，按账单成员顺序分别为 33.34、33.33、33.33 元。余下的分币固定分给排在前面的参与者，**不是随机或轮流分配**。1 分钱也可以在多人间分摊，部分成员此笔为 0 分。
- 自定义模式下各人金额必须非负、总和精确等于这笔费用。没有分摊的人取消勾选即可；至少一位成员参与。
- 净额 = 已付 − 应摊。正数表示应收，负数表示应补。服务按净额生成确定性的贪心抵扣建议，最多人数减一笔转账，**不保证全局最少笔数**；每一分钱守恒。建议可能让两位未直接互相垫付的成员之间转账，这是净额抵扣，不是原始欠款凭证。
- 最多每账号 100 个账单（含回收站）；这些限制控制本机快照体积。无自动汇率、税费、利息或利率计算。

## API 与开发

- `GET /api/v1/splits`：返回当前账号所有账单（含回收站）及 Go 计算的 `report`。
- `PUT /api/v1/splits/{id}`：创建或整体更新账单。创建用 `revision: 0`，更新用当前版本；标识为 8–80 个字母/数字/下划线/连字符。禁止客户端覆盖用户、创建时间、计算报告等字段。
- 输入为 `title,date,note,members,expenses,state,deleted,revision`。`state` 为 `open|settled`；`expenses[].amount_cents` 与 `shares[].amount_cents` 都是整数分。
- `equal` 模式中 `shares` 指定参与者（可提交金额 0）；服务按账单成员顺序重算分摊并规范化顺序。`exact` 模式验证金额总和。保存整个账单与版本检查在同一仓储锁内原子完成。
- 相同版本的原请求在紧接着的成功保存后重试，返回原结果而不增加版本。若中间已有新修改，则返回 409；不要重用旧请求覆盖最新账单。
- 已认证接口，响应 `Cache-Control: no-store`。400 校验错误，401 未登录，404 当前账号无该账单，409 版本冲突。详见 OpenAPI。
