## 1. 产品定位与规划前提

建议定位：**一个自己愿意每天打开的个人生活工作台，在电脑上整理，在手机上随手记录、查看和处理。**

它以日历、待办、记录和常用生活工具为核心，学习与探索按需使用。后续主要衡量「一件日常小事能否更快完成、数据能否放心保存、换个设备是否顺畅」，而非增加多少页面。

本计划先以你个人使用、现有 Go 服务和安卓手机为前提。保留已经选择的「安卓 App 连接电脑服务」模式，先完成可安装、可验证的内测版。面向公众、付费或团队使用属于后续独立决策，不能直接把当前个人内网服务当成公网产品发布。

高频与低频的判断是产品假设，尚未读取或统计你的实际使用行为。建议连续自用两周，用简单的问题记录验证这些假设，不默认上传使用数据。

## 2. 当前基线与实际缺口

| 已有基础 | 需要继续解决的问题 |
| --- | --- |
| 24 个功能页面，支持整理导航与快捷命令 | 新功能分散，部分工具要展开多个入口才能找到；默认 12 个常用项仍需依据实际习惯调整。 |
| Go 标准库 HTTP、服务与仓储分层、账号隔离、事件总线 | 新增模块仍需要触及较大的共享文件；跨模块事务、后台任务可靠性需要更明确的边界。 |
| 内存仓储、JSON 周期快照、滚动备份与损坏恢复 | 默认每 15 秒尝试快照，成功响应不等于立即落盘；异常退出可能丢失最近修改，持续写盘失败会扩大窗口。 |
| 个人 JSON 导出、独立文件快传目录 | JSON 导出不包含快传文件及其元数据；还没有经过完整演练的一体化备份恢复产品流程。 |
| 草稿提示、退出保护、部分接口原样重试与版本冲突保护 | 草稿大多只在页面内存；刷新、进程终止等场景仍可能丢失。各模块保存规则和错误处理并不完全统一。 |
| 安卓工程、本地打包界面、电脑连接设置、原生文件与剪贴板通道 | 尚无 APK 构建和真机验收记录；本机检查只发现 SDK 30，现有工程配置需要 SDK 36。 |
| 深浅色、手机适配、共用交互设施 | 仍需按完整流程验证大字号、软键盘、返回键、弹窗、息屏与恢复，不能仅凭截图判断可用。 |
| 54 项前端冒烟脚本、Go 测试与静态检查 | 多数前端测试模拟 DOM 或原生接口；仓库未发现发布 CI 工作流，真实浏览器与 Android 构建需要进入持续验证。 |
| 新闻、天气、词书、阅读等丰富内容 | 外部依赖仍可能不可达或过时，需要最后可用内容、更新时间和失败降级。 |

代码规模提示：本次检查有 56 个前端 JS 文件，`app.js` 约 2982 行，`memory.go` 约 1742 行。行数本身不是缺陷，但继续往共享控制器追加功能会增加修改和回归成本。

### 导航与首页的改进

- 桌面保留现有分组侧栏，首页允许用户选择少量常用卡片、排序和收起。先做简单固定尺寸布局，不急于做任意拖拽编辑器。
- 安卓首个内测版沿用现有导航完成验收；随后评估「今天、日历、记录、工具、我的」四至五个底部入口，作为现有功能的聚合入口。先在真机验证原型，再决定是否替换侧栏。
- 「我的 / 设置」应集中连接地址、账号与设备、主题、字号、数据备份、权限、版本和诊断。目前这些设置分布于多个入口，适合优先收纳。
- 功能不常用时先降级入口；真正删除前提供数据导出、引用核对、兼容跳转及明确的迁移方案。

## 4. 分阶段交付

以下 R0–R4 是规划编号，不是已发布的版本。建议一个迭代控制在 1–2 周；单人兼职时按可用工时缩小范围，不以赶日期替代验收。数据库迁移和离线同步各自需要单独评估，不能承诺一次迭代覆盖全部页面。

### R0：建立可用内测基线

目标：先让你能在自己的安卓手机上每天使用，并知道当前数据和连接状态。

优先任务：

1. 补齐 Android 构建环境，生成调试 APK，记录版本和构建来源，完成首次安装及覆盖升级。
2. 验证登录、待办、日历、备忘录、专注、文字快传、文件保存七条核心链路；建立已知问题清单。
3. 增加统一设置入口的最小版本：电脑连接、版本信息、权限说明、同步状态和脱敏诊断导出。
4. 将 Go 测试、`go vet`、前端冒烟与 Android 编译接入 CI；增加真实浏览器核心流程测试。
5. 显示最近一次成功快照时间、失败状态及现有备份范围，提供停服后完整备份的清晰操作说明。

验收：

- 你的手机可以安装与升级，原账号可登录；重启 App 后记录与身份状态符合预期。
- 手机创建待办、备忘录或文字片段后，网页能够回读；反向修改也可同步核对。
- 电脑暂时离线时有明确说明，输入不会被一次错误响应清空；恢复连接后可手动继续。
- 系统返回键、键盘遮挡、录音拒绝权限、系统保存窗口取消等流程可完成。
- CI 能生成可追溯的构建结果；模拟桥接测试不替代真机验收。

### R1：把数据保障做成产品能力

目标：保存规则明确，能够备份、核对和恢复，升级时有退路。

优先任务：

1. **数据中心**：展示数据与附件占用、备份状态、导出范围；实现备份清单、内容校验和恢复预览。
2. **SQLite 仓储验证及迁移**：验证事务、索引、迁移版本、Windows 构建和备份能力，逐步补齐现有领域的数据映射及仓储契约测试。
3. 统一关键写操作的版本检查、请求标识和结果确认，先覆盖记录文本、日历、待办、财务及文件元数据等高价值数据。
4. 首先为备忘录、心情、长文本和周复盘补本机草稿恢复；按账号和服务地址隔离，支持查看与清理。
5. 建立数据升级演练：完整备份、在独立目录迁移、核对记录和引用、试运行，最后显式切换。

迁移约束：

- 原型可先使用一小部分领域数据验证，但生产切换必须检查全部受影响的模块和跨模块事务；不能只迁移几张表后就宣称整站事务化。
- 明确待办重复生成、任务引用、日历联动、运动记录等一致性边界。生产环境保留一个权威写入来源，避免 JSON 与 SQLite 两套可写主数据长期并行。
- JSON 保留为兼容导出或迁移来源。回退前必须先保全切换后的新增记录，不能直接用旧快照覆盖新数据。
- 数据库迁移不负责自动找回之前没有成功保存的内容，也不自动同步其他设备。

验收：

- 「已保存」有明确的持久化承诺；关键事务测试中，程序被强制结束后已确认提交的数据能恢复，未确认操作可以核对。
- 备份恢复到独立测试目录后，能核对记录数、关键字段、跨模块引用和附件哈希；附件缺失会报告。
- 恢复包损坏、版本不兼容、其他账号数据或配额超限时，预览阶段就能阻止破坏性恢复。
- 草稿能在普通刷新和 App 被结束后恢复；退出、换账号、换服务器及共享设备下的保留策略清楚可控。

SQLite 具备事务机制，但实际持久化还需明确配置与故障测试；在线备份应采用一致性备份机制，而非直接复制运行中的文件。技术依据：[SQLite 事务](https://www.sqlite.org/transactional.html)、[SQLite 在线备份](https://www.sqlite.org/backup.html)。

### R2：让跨端使用形成稳定体验

目标：减少手机对“电脑此刻在线”的依赖，并补齐真正的移动端能力。

先做：

- 最近已成功读取内容的本机缓存，标注更新时间与离线状态，离线时仍能查看。
- 为已完成的记录类流程保留本机草稿，恢复联网后由用户确认提交；先不自动重放删除、重复任务生成、训练状态流转等复杂操作。
- 统一显示「本机草稿、等待同步、已提交、需核对」；网络失败、同步成功和持久化成功分别表达。
- 为客户端与服务增加兼容性信息、升级说明及不兼容提示，延续现有 `mobile-info`，避免旧 APK 对新接口反复报错。
- 将轻提醒、日历与专注提醒纳入统一规则：去重、稍后、免打扰、权限状态和回到前台的状态校准。
- 原生令牌存储与设备会话管理：支持识别设备、注销当前设备、撤销旧设备会话。不能只在本地删除令牌后就宣称服务端已经撤销授权。

再决定是否扩大离线写入。若需要，先选备忘录和简单待办做有限试点，明确：客户端生成稳定 ID、幂等提交、增量同步游标、删除标记、冲突副本与人工合并、账号切换隔离以及同步标记保留期限。不得静默按“最后写入”覆盖长文本，也不能因为换成 SQLite 就认为跨设备同步已经完成。

安卓后台任务要按实际语义选择机制：后台整理与用户指定的时间提醒分开设计，精确提醒需按平台要求处理权限与撤销；不承诺所有设备上都能不受休眠和省电影响。技术依据：[Android 闹钟与后台调度说明](https://developer.android.com/develop/background-work/services/alarms)。

验收：断网、息屏、进程被结束、重启设备、权限拒绝 / 撤销、重复提交及双端同时编辑都有明确结果；以你的真机和至少一个模拟器系统版本为首轮支持范围。

### R3：深化现有功能，减少重复操作

目标：让模块之间自然联动。每个迭代只选一个完整场景。

| 场景 | 建议升级 | 需要守住的边界 |
| --- | --- | --- |
| 早晨安排一天 | 今天页集中今日待办、日程、到期事项，快速记录后可选转成待办 | 不把全部数据堆进首页，不重复保存同一件事。 |
| 临时想法变行动 | 从备忘录创建待办，双方保留可访问的来源；完成后可返回原文 | 转换与复制含义清楚，删除或归档后引用不会导致错误。 |
| 执行与专注 | 从待办启动专注，专注完成后由用户决定是否完成待办 | 专注结束不能自动等同于任务完成，也不虚增投入记录。 |
| 日程与周期事项 | 统一查看待办、保养、订阅、重要日子和运动；点击返回原记录 | 日历作为视图聚合，避免再造一份可漂移的业务副本。 |
| 日常收支与订阅 | 快速记账、分类与重复录入减负；订阅付款可显式生成一次账本流水 | 不因页面刷新、撤销或重试重复记账，不自动读取金融账号。 |
| 买到与用完 | 购物完成后可选进入物品管家；保修、到期与借还更易查找 | 只填写必要字段，尊重用户选择，保留原始来源。 |
| 阅读与英语 | 已下载内容优先、本地阅读记录、最后可用资讯和来源状态 | 下载失败与没有内容区分；新内容不覆盖笔记，阅读进度不被旧请求倒退。 |
| 学习任务与待办 | 先统一入口和筛选，再验证是否合并底层模型 | 明确目标、估时、状态、专注和日历引用映射，迁移可验证。 |

### R4：根据真实使用决定长期形态

在 R0 真机自用两周之后记录选择，避免同时开发三套路线：

| 路线 | 适用情况 | 后续投入 |
| --- | --- | --- |
| 保留电脑服务 | 主要在家或办公网络使用，电脑经常开机 | 稳定启动、数据目录、局域网连接和健康状态；按需探索常开设备。 |
| 常在线服务 | 希望外出也随时访问同一数据 | 单独设计 HTTPS、部署、访问控制、备份、监控和成本；完成审查后再部署。 |
| 更完整的离线 App | 希望电脑关机后仍能独立记录、提醒和阅读 | 本地持久化、离线身份边界及同步协议是独立工作包；先完成有限离线试点。 |

当前默认继续第一条路线，不在本轮切换部署或重写客户端。如果以后公开使用，还需要补充账号恢复、会话撤销、权限与配额、升级回滚、隐私数据生命周期及故障响应，之后再讨论收费或应用商店发布。

## 5. 技术演进原则

### Go 后端

- 继续采用 `net/http` 和模块化单体，利用现有结构迭代，不安排单独的框架迁移版本。
- 按「日程与任务、记录、生活工具、成长内容、平台能力」梳理领域依赖；按实际调用收窄仓储接口，减少每个新功能必须修改大接口的情况。
- 请求取消、超时、有界并发、优雅停机和结构化日志已有基础，下一步补充可观测的结果及持久化任务语义；业务事件在事务成功后发布。
- 需要可靠执行的提醒或同步任务采用可持久化状态及去重；不把只存在内存中的事件队列视为可靠任务账本。
- 持续验证竞态、并发更新、慢外部接口和磁盘故障。核心写入测试关注结果和恢复，不只检查 HTTP 返回码。

### 前端与设计

- 先提取共同 API 客户端、账号隔离、取消、版本冲突及草稿处理，再逐步拆分 `app.js`；一次覆盖一个领域，保持可回归。
- 基于现有页面逐步收敛颜色、字号、间距、按钮、表单、空状态、错误状态与弹窗。可先用 JSDoc / 类型检查明确数据契约，再决定哪些模块适合迁移 TypeScript。
- 在现有构建基础上评估页面按需加载及资源版本管理，避免启动时一次执行全部功能脚本；网页版与 APK 共享资源来源并记录构建版本。
- 动画服务于状态变化：展开、切换、保存结果和返回反馈；尊重系统减少动态效果与大字号。主要操作在手机上易点击，关键说明不依赖小字或悬停。
- 建立一套固定视觉验收场景：空数据、较多数据、长标题、请求失败、离线、冲突、深浅色、390px 窄屏及键盘弹出。

### 质量与发布

- CI 先跑现有检查，再逐步加入真实浏览器流程、Android 编译与升级测试；发布记录区分模拟接口测试、真实浏览器测试和真机测试。
- 为每次发布记录版本、变更、已知限制和回退步骤；构建产物能对应到代码版本。
- 全部测试使用临时数据。迁移与恢复演练使用备份副本，验收完成前不覆盖实际数据。
- 外部资讯和天气先保证缓存、超时、来源标识与重试可理解，再扩充来源；AI 保持可选，核心流程不依赖其授权或在线状态。

## 7. 暂缓方向与新功能准入

暂缓：继续增加一级功能页、全站一次性换前端框架、单独切换 HTTP 框架、多人协作 / 社交体系、完整离线双向同步、全模块接入 AI，以及未经数据与部署准备就开放公网。

后续新功能先回答：

1. 你会在什么明确的日常场景打开它？现有功能是否已经能完成？
2. 用户第一次操作能否很快得到结果？是否需要持续大量录入？
3. 能否作为已有页面的一项能力，复用账号、搜索、日历、备份与交互设施？
4. 在断网、权限拒绝、外部来源失败时，有没有可理解的使用方式？
5. 谁负责它的数据删除、导出、恢复、版本冲突和长期维护？

如果真实使用证明值得继续扩充，可优先考虑「可重复使用的出门 / 采购 / 检查清单模板」或「拍照提取文字并送入备忘录 / 待办」。它们复用现有入口；图像文字识别需另行验证识别质量、离线能力、权限和数据去向，不在本计划中假定已有。

## 8. 每轮复盘方式

每个迭代只选一个主要用户目标，记录：新增了什么、缩短了哪条操作路径、修复了什么失败场景、哪些结果还未验收。只要没有完成数据与真实设备验收，就保留相应限制说明。

两周自用后，回答四个问题：最常打开哪些入口、哪里需要重复输入、哪次出现保存或同步疑虑、是否经常因为电脑离线无法使用。可手工记录；若以后增加本机使用计数，应允许关闭和清理，且不记录正文、取件码、剪贴板内容或细粒度按键。

路线调整依据使用事实：高价值入口继续深化，低使用率且没有独特用途的入口收纳或退役；每次退役单独处理数据与兼容，不直接删除记录。
